# Обзор
Платформа ориентирована на сбор, обработку, хранение и анализ разнородных данных: карты, таблицы, фото.

Основная идея архитектуры — разделение ответственности по типам данных и сценариям использования:
* тяжёлые файлы, временные ряды и расчётные продукты хранятся в объектном хранилище;
* геометрия и serving-ориентированные пространственные представления — в геопространственной БД;
* нормализованные атрибуты и справочники — в реляционной БД;
* обработка, аналитика и маршрутизация вынесены в отдельные вычислительные контуры.

## 1. Основные требования
Ключевые требования, заложенные в архитектуру:
* Поддержка разнородных геоданных: векторы, растры, time-series.
* Работа с временными слоями (прогнозы, аналитика).
* Быстрый доступ для интерактивной карты (WMS/WFS, тайлы).
* Масштабируемое хранение больших файлов (NetCDF, GeoTIFF, отчеты).
* Нормализованные экологические данные с гибкой фильтрацией.
* Автоматические ETL-пайплайны из внешних источников.
* Поддержка аналитики, расчетов и ML.
* Разделение online-нагрузки (карта, API) и offline-обработки.
* Возможность хранения истории и агрегированных представлений.
* Прагматичность и возможность поэтапного развития.

Приложены отдельным файлом                        

## 3. Основные компоненты
Архитектура описана по слоям с явными потоками данных.

### 3.1.Источники
* EXT_API: внешние API (GFS, Ocean Models, AIS)
* SAT: спутниковые данные (Sentinel, GIBS)
* USERS: пользовательские загрузки (CSV, SHP, фото)

### 3.2.Ingestion

Источники данных:
* внешние API и FTP (GFS, Ocean Physics, AIS);
* спутниковые каталоги (Sentinel, GIBS);
* пользовательские загрузки (CSV, XLSX, SHP, GeoJSON, фото).

Подход:
* все данные сначала сохраняются в raw-слое объектного хранилища;
* ingestion происходит батчами по расписанию;
* выполняется базовая валидация форматов, схем и целостности.

Инструменты:
* оркестратор: Airflow / Prefect;
* Python, GDAL, xarray, pandas.

### 3.3. Storage

#### 3.3.1 Объектное хранилище (S3-совместимое)

Центральное хранилище тяжёлых и временных данных:
* спутниковые снимки и растры;
* NetCDF / GRIB архивы прогнозов;
* агрегированные time-series;
* отчёты, фото, ML-артефакты.

Логическая структура:
* raw/ — исходные данные;
* processed/ — нормализованные и конвертированные данные;
* aggregated/ — временные агрегаты;
* products/ — конечные расчётные продукты.

#### 3.3.2. Геопространственная БД (PostGIS)
Используется для serving-ориентированных пространственных данных:
* векторные слои и объекты;
* spatial-индексы;
* упрощённые и агрегированные временные слои;
* маршруты судов и навигационные продукты.

Хранилище не является primary store для полной истории растров и прогнозов.

#### 3.3.3. БД атрибутов
Назначение:
* экологические и нормативные данные;
* справочники и классификаторы;
* параметры расчётов и метаданные.

Особенности:
* строгие схемы (3НФ);
* связи с геометрией по ID;
* расширяемость через reference-таблицы.

#### 3.3.4. База метаданных

Назначение:
* Центральный каталог всех датасетов, слоёв и производных данных.
* Хранение информации о версиях, источниках, формате и статусе обработки.
* Связь raw/processed/aggregated данных с геометрией и атрибутами.
* Поддержка lineage и контроль актуальности данных.

Особенности:
* Описание датасетов (тип, источник, формат);
* Временной охват (start/end time);
* Пространственный охват (bbox, CRS);
* Версии и состояние обработки (raw/processed/aggregated/serving);
* Ссылки на физическое хранение (S3 paths, таблицы PostGIS/PostgreSQL);
* Метаданные пайплайнов обработки.

### 3.4. Processing

Каждый процесс Processing является отдельным узлом:
* конвертация NetCDF → GeoTIFF
* обработка векторных данных
* агрегация временных рядов
* обработка с использованием ML-моделей
* батч аналитика (индексы, ПДК)

Входящие данные:
* S3_RAW → RASTER, TS, ML
* POSTGIS → VECTOR, TS
* PostgreSQL → ANALYTICS

Исходящие данные:
* RASTER → S3_RAW
* VECTOR → POSTGIS
* TS → S3_RAW, POSTGIS
* ML → S3_RAW
* ANALYTICS → PostgreSQL, S3_RAW, POSTGIS

Все процессы → Metadata Database (версии, lineage)

### 3.5. Слой предоставления
* геосервисы (WMS/WFS/Tiles)
* прикладные API
* сервисы построения маршрутов
* сервисы формирования отчетов

Потребители: MAP, APPS, NOTEBOOKS.
Используют подготовленные данные из PostGIS, PostgreSQL и S3_RAW.

### 3.6 Аналитические витрины (итоговые потребители)
* интерактивная карта
* выгрузка по API конечным потребителям
* подготовка аналитических дашбордов


## 4. Технологический стэк

* Геоданные: PostGIS (+ GeoServer)
* Object Storage: MinIO / AWS S3
* Реляционные данные: PostgreSQL
* Аналитика: DuckDB / ClickHouse (перспективно Spark)
* ETL / Оркестрация: Airflow / Prefect

## 5. Ключевые решения и trade-off’ы

**Стартовая архитектура**
Облако (вероятно yandex) + PostGIS + PostgreSQL
* Все тяжелые данные (растры, NetCDF, фото) → Объектное хранилище (облако или локально)
* Только ключевые векторные слои и метаданные → PostGIS для быстрого доступа через API
* Табличные экологические данные → PostgreSQL

Плюсы
* относительно просто разверенуть PostGIS и PostgreSQL
* фокус на data ingestion: основной сложностью представляется сбор и нормализация данных, а не их хранение
* относительно экономично

Минусы
* растровые слои из облака будут загружаться медленнее, чем из специализированного tile-сервера
* сложно джойнить данные между postgis, облаком и postgresql

**Обработка данных батчами (без потоковой обработки)**
* Все пайплайны — батчевые, обработка раз в сутки (или в несколько часов - по необходимости0
* ML-обработка вынесена в отдельные notebook/скрипты, не интегрирована в основную оркестрацию

Плюсы
* относительная простота реализации
* батч обработку проще отлаживать, чем стриминг, легче поправить обработку и пересчитать за предыдущие периоды
* относительная экономичность по сравнеию с раазработкой потоковой обработк на Kafka

Минусы
* нет real-time картины

**Технологический стек**
Фокус на российских и open-source решениях.
Для быстрого старта использовать комбинацию управляемых и self-hosted решений:
* Управляемая база данных: Yandex Managed Service for PostgreSQL с поддержкой расширения PostGIS для работы с геоданными.
* Управляемое объектное хранилище: Yandex Object Storage (S3-совместимое) для хранения файлов и данных.
* Оркестрация процессов: Apache Airflow, развернутый на виртуальных машинах Yandex Compute Cloud.
  
Плюсы
* снижение сложности администрирования архитектуры: можно сфокусироваться на логике обработки данных
* переносимость: впослеедствие можно будет переехать на собствнную инфраструктуру
* доступность сервисов: ру-техподдержка, нет сложностей в оплате

Минусы
* потенциально дополнительные затраты (но отчасти компенсируются ускорением внедрения)
* зависимость от вендора

**Итоговый план MVP**
На старте
* PostgreSQL + PostGIS  — для всего, что требует SQL и быстрого доступа
* yandex object storage — для всего остального (растры, файлы, архивные данные)
* Airflow в managed версии или Docker — для оркестрации ETL
* Python FastAPI — для API поверх PostGIS и метаданных
* Простейший фронтенд на Leaflet/OpenLayers — для демонстрации возможностей

Направления доработки по мере необходимости
* специализированное хранилище для тайлов
* потоковые пайплайны 
* интеграция ML-пайплайнов

## 6. Риски и упрощения

Риски:
* финансовые: большой объем растровых данных + изменение политик вендора могут значительно увеличить косты
* обработки и согласованности: сложный формат данных делает введение новой структуры данных или изменения старой структуры очень трудозатратным -> чееловеческий фактор ошибки в обновлении пайплайнов
* Time-series данные могут перегрузить GeoDB без агрегаци
* Разнообразие входных форматов усложняет валидацию

Упрощения:
* Нет отдельного streaming-контура
* локальный ML в ноутбуках
* Data governance и lineage упрощены.
* специализированное tile-хранилище на потом
* минимальные алерты и мониторинг
